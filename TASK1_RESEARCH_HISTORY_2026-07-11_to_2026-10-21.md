## §0. Background — what Task 1 is, and where it stood on 2026-07-10 (last known state before this window)

Task 1 classifies every animal/plant mention extracted from the 925-novel + 88-bestseller corpus as either:
- **référentiel** — the term refers to a real, physically present animal or plant (literal use)
- **figuré** — the term is used as a metaphor, comparison, idiom, or symbol

It is a prerequisite for Tasks 2, 3, and 4.5, which only operate on référentiel (for Task 3) or figuré (for Tasks 2/4.5) mentions. Riccardo approved it in the first project meeting ("task one is okay with me, you can go ahead and apply to the entire corpus"), as an improvement over Joanna's earlier ChatGPT-based classification (~47%, or ~16% per another transcript reading).

Model: qwen3:30b via Ollama, temperature 0, thinking mode **mandatory** (num_predict=100/no-think collapses figurative accuracy to 0%; the final production setting is num_predict=5000, 9.4s/row baseline). Final prompt (v6) uses 7 core définitions plus worked examples, reached after an earlier v2 prompt was found to have **leaked gold-set examples into the prompt itself** (a bug that produced an invalid 92.6% number, fixed in v3 by replacing every leaked example with an independently-sourced one — this is the origin of the project's later standing rule that prompt examples must never come from the gold set). A v4 "two-pass" classification approach (ask "clearly référentiel?" first, fall back to a figuré-focused second pass only if uncertain) was tried and **reverted** — it scored worse on all three categories, because the second pass saw strictly less context than a single comprehensive prompt.

To make the full corpus tractable before the July 15 internal deadline, batching (N rows per API call) was tested and **batch=4 was chosen** (3.9s/row, identical animaux figurative accuracy to single-row v6, 1-item difference on plantes) — projected total runtime ~8.5 days (animaux 5.8d + plantes 2.7d) vs. ~20 days unbatched.

**State as of 2026-07-10, end of day** (the last fully-documented checkpoint before this document's window begins):
- **Animaux: done** (2026-07-05, including a retry pass `retry_animaux.py`/`retry_animaux_v2.py`). 127,935 rows, 89,675 référentiel / 38,260 figuré (29.9% figuré).
- **Plantes: done** (2026-07-10 07:28, 19.8h run, plus two retry passes resolving 376/444 then 36/68 of initially-failed rows; 32 rows, 0.05% of corpus, permanently unresolved and defaulted to référentiel). 69,468 rows, 59,967 référentiel / 9,501 figuré (13.7% figuré).
- **Loterre: not run on the full corpus at all.** Existed only as a 189-row gold-set benchmark (`evaluate_loterre_v8.py`, 85.2% raw / 88.9% corrected accuracy after a manual mislabel audit) developed during prompt iteration. The full climate-change/Anthropocene-vocabulary corpus (108,425 raw Loterre-term mentions per the original corpus README stats; ~130,572 candidate rows once the actual production input files were later built) had never been pointed at by the production pipeline. `MASTER_DOCUMENTATION.md` (written sometime in this gap, exact date unclear) explicitly states this and estimates a full run at ≈117.5h ≈ 4.9 days at the batch=4 rate — framed as an open, undone item.
- **Final gold-set audit** (manually read all 33 rows where gold=figuré but the model said référentiel, across all three sets): found **13 confirmed gold-set mislabels** (the model was actually right) and 4 genuine borderline judgment calls. Corrected accuracy: Animaux 91.8% (157/171), Plantes 98.4% (183/186), Loterre 88.9% (168/189, scored on the older v8 eval script, not the current production prompt).
- **100-random-sample manual spot-checks** (independent of the gold sets): Plantes 92/100 clean, Animaux 90/100 clean — corroborating the gold numbers.
- **The Task 1 duplicate-process incident** (2026-07-09 morning): an unattended orchestrator script's kill command targeted a PID that was off-by-one from the real process, never verified the kill succeeded, and relaunched a second instance of `run_task1_corpus.py --category plantes` while the first was still alive. Both wrote to the same output file for ~7.5 hours, producing 3,529+ exact-duplicate rows (confirmed via `lsof`, same inode). Fixed by killing both, backing up the corrupted file, deduping via `csv.reader` (not naive line-splitting, which gave false corruption signals on rows with embedded newlines), and relaunching a single instance. Root cause: the resume logic has no locking between concurrent instances. Standing lesson from this incident: never trust a script's own "process stopped" log line — always independently verify via `ps`/`pgrep`.
- **An O(n²) resume-scan bug** (found and fixed 2026-07-08, on the very first restart of the plantes run): the script did a linear scan through all ~69K rows per already-done row (~1.3 billion comparisons) — fixed to an O(1) dict lookup.
- Riccardo's own published paper (*"Le tournant écologique à l'épreuve des humanités numériques"*) was used as an external benchmark: human inter-annotator agreement on this exact literal/figurative task is only 76% (Cohen's Kappa = 0.64) — meaning this project's 91.8%/98.4% corrected gold-set numbers for animaux/plantes already exceed the human-agreement ceiling, a fact explicitly communicated to Riccardo as a reason not to chase marginal accuracy gains further. Also noted: this project's own corpus-wide figurative rate for animals (29.9%) is roughly double Riccardo's own pre-existing published estimate (15.5%) — flagged as a real, checkable discrepancy, not silently reconciled.

## §3. 2026-10-05 to 2026-10-07 — the animal-forms lexicon gap (§0-Foundations work that fed new rows into Task 1)

This is not Task 1 itself, but directly produced new candidate rows for it, so it belongs in this history.

**Background (email from Riccardo, 2026-08-20, 10:46 AM)**: Riccardo found a real gap in the existing animal lexicon (`lexiques/ANIMAUX.txt`) — it only ever connected singular/plural forms of the same lemma (chien/chiens→chien), never feminine forms (chienne/ourse/lionne) or young-animal forms (louveteau). He sent an attachment, `20aug/animaux féminin petit(2).xlsx`, listing 99 unique derived word forms across ~70 animal lemmas, and flagged two words needing disambiguation himself: `chatte` (female cat vs. anatomical slang — "needs an automatic distinction," his words) and `chenille` (caterpillar vs. fairground ride — "I think I can check those manually," his words). He also flagged 6 forms with more than one possible parent species, resolved later by email on 2026-09-19: **cabri & chevreau → chèvre, génisse → taureau, chamelon → chameau, nourrain & porcelet → cochon.**

**2026-10-05 — scope decision**: rather than just fixing the lexicon and recalculating the Shannon biodiversity index (Riccardo's literal ask), Labiba decided to propagate the fix through Tasks 1, 2, 3, and 4.5 too, so every downstream number stays consistent with the complete lexicon. This was an explicit, deliberate scope expansion beyond what Riccardo asked for, not a default behavior.

**Real homograph evidence gathered** (pulling and reading actual corpus sentences, not relying on general-knowledge guesses — later formalized as a standing project lesson, see `feedback_verify_homograph_risk_with_real_samples.md`): initial raw-count-based risk flags on `rate`, `mule`, `ourse`, `laie` (beyond Riccardo's own `chatte`/`chenille`) turned out to be substantially wrong once real sentences were actually read:
- **chatte**: confirmed genuinely risky — ~75-80% anatomical slang in a 25-sentence sample, only ~20-25% genuine animal.
- **rate**: not what was guessed. ~70-75% of raw occurrences are the *verb* "rater" (to miss/fail), not a noun at all. Of the remaining noun occurrences, 100% in the sample were "spleen," 0% were "female rat." A POS-tag filter (`fr_dep_news_trf`) eliminated most of the noise cheaply.
- **mule**: wrong guess corrected — the dominant competing sense was "mule" as drug courier, not shoes as originally assumed. Genuine animal/idiom readings were actually the majority (~60%).
- **ourse**: wrong guess corrected, risk overstated — 24/25 in the sample were the literal animal; only one was the Ursa Major constellation sense.
- **laie**: low volume (18 total), animal sense dominates.
- **chenille**: richer than Riccardo's own binary framing — real sentences also showed "faire la chenille" (a conga-line wedding dance), tank/vehicle tread, and chenille fabric (quilting material) as genuinely competing senses, at least 4-5 distinct senses, not 2.

**Work completed 2026-10-05 to 2026-10-07**:
- `lexiques/ANIMAUX.txt`: 99 new forms appended (18,916→19,015 lines).
- `lexiques/animaux_formes_derivees.csv` (new file): 99-row form→reference-lemma mapping, Riccardo's 6-form resolution applied.
- `lexiques/categories_animales/*.txt`: 98 of 99 forms added (MAMMIFERES +57, OISEAUX +28, POISSONS +7, INSECTES +2, REPTILES +2, AMPHIBIENS +2; `vermisseau` has no category, stays "autre"). `chenille` deliberately excluded entirely, pending Riccardo's own manual determination — adding it now would inject its 4+ non-animal senses into `papillon`'s species count, requiring a later correction.
- `homographie/isAnimal/homographie_train.csv`: extended with 140 hand-labeled `chatte` sentences (57 animal / 83 slang) and 88 hand-labeled `rate` noun-occurrences (7 genuine animal, 81 spleen) — real animal signal in `rate` across all 420 raw occurrences: only 7 (1.7%).
- **A chatte-specific FlauBERT classifier was trained** (extending `homographie/isAnimal/train_homograph_binary.py`, 2,049 filtered binary training rows after excluding 368 pre-existing multi-class rows that would otherwise crash a 2-class model, 20 epochs, 431 seconds on GPU, final train_loss 0.13). Holdout accuracy: **83.3% (25/30)**. Applied to the full 819 staged `chatte` rows: 297 predicted animal (merged into production), 522 predicted not-animal (discarded).
- Extraction for all 98 non-chenille forms completed: 5,149 raw rows extracted (4,704 corpus_principal + 445 bestsellers); after filtering, 4,211 total rows merged into production (96 clean forms' 3,907 rows + rate's 7 confirmed rows + chatte's 297 classifier-confirmed rows). Final production file sizes: `ENTITES_contexte_animaux.csv` 114,851→**118,746**; `BESTSELLERS_contexte_animaux.csv`→**13,410**.

A heads-up email combining the rate/mule/ourse/laie findings (reported as completed work) and a status check on Riccardo's chenille review was drafted 2026-10-07; confirmed sent 2026-10-07. **No reply had been received as of the last record checked for this document** — chenille remains excluded from the corpus to this day as far as this document's sources can confirm.

## §5. The Loterre full-corpus run — launch window, crash, and ongoing run

**Exact launch date not recoverable.** The earliest direct evidence is the log file `métaphore/loterre_full_corpus_log.txt`, timestamped **2026-10-16 00:47**, which is 0 bytes — consistent with a run that started and then crashed almost immediately (see below), but this does not rule out an earlier, completely unlogged attempt. `MASTER_DOCUMENTATION.md`'s framing (Loterre "not yet run on the full corpus," estimating ~4.9 days) is undated more precisely than "sometime in the undocumented gap or very early October," so it cannot be used to narrow the window further than "launched on or shortly before 2026-10-16."

**What the run is**: `métaphore/run_loterre_corpus.py` classifies candidate rows against Loterre thesaurus terminology (climate-change/Anthropocene vocabulary), using the exact v8 prompt finalized 2026-06-24 (85.2% gold accuracy) imported unchanged from `evaluate_loterre_v8.py` — per the project's standing rule to reuse validated prompt functions for production runs rather than re-describing them. Input: `resultats/corpus_principal/ENTITES_contexte_loterre.csv` + `resultats/bestsellers/BESTSELLERS_contexte_loterre.csv`, combined **~130,572 candidate rows**. Output: `resultats/task1_loterre_labels.csv`. Checkpoints every row, resume-safe by design, expected ~5-day runtime.

### 2026-10-16 — disk-quota incident crashes the run

Earlier the same session, two alternative models were tested as Task 2 candidates (unrelated to Loterre directly, but the cause of what follows): **DeepSeek-R1:32b** scored 59.6% vs. qwen3:30b's 63.8% on the same dev rows (rejected, worse); **Gemma3:27b** (17GB) never produced a usable data point — every load attempt crashed with `GGML_ASSERT(rc == 0) failed` immediately after the log showed it reserving **Vulkan** compute buffers instead of CUDA, an apparent Ollama 0.40.5 GPU-backend-selection bug on this server unrelated to disk space; rejected, deleted.

Pulling Gemma (17GB) plus reinstalling a newer Ollama release's `lib/` directory (~2.1GB) pushed total disk usage on `/dev/md1` over the **105GB hard quota** (`/home/farooq/...` and `/raid/home/farooq/...` share the same underlying filesystem/quota pool). This silently crashed the Loterre job mid-write — its output-file write almost certainly failed when the quota was hit — leaving exactly **one** truncated trailing row (fields parsed as `None`, e.g. `fichier` cut off mid-string); the other 2,423 rows already written were fully intact. The crash was invisible until a routine check: `ollama ps` showed nothing loaded, GPU utilization had dropped to near-idle, and no `run_loterre_corpus.py` process remained — none of which throws an obvious alarm on its own.

**Fix applied**: removed the one malformed trailing row; hardened `run_loterre_corpus.py`'s resume logic (around the `done_keys` computation) to skip any row with a `None`/missing field instead of crashing with `TypeError: 'NoneType' object is not subscriptable` on the next restart; freed disk space by deleting `deepseek-r1:32b` (34GB, already rejected) and a genuinely stale separate directory `/home/farooq/projects/ecopoetique` — no `_v2` suffix, confirmed by checking it had a different inode than `ecopoetique_v2` before deleting it (4.5GB freed). Final usage after cleanup: ~68GB/105GB. Restarted cleanly (this is the `loterre_full_corpus_log2.txt`, timestamped 2026-10-16 01:23); confirmed genuinely resuming via the real output file's row count climbing over time and GPU utilization returning to 96% — explicitly **not** trusted via `ps`/`pgrep`, which kept self-matching the grep command's own command-line text and producing false "it's running" positives.

**General lesson recorded from this incident**: disk-quota-exhausting side-work (pulling/testing other models) can silently kill an unrelated, multi-day production job sharing the same quota pool, without failing loudly. Check `quota -s` before pulling/testing another large model.

### 2026-10-16 to 2026-10-19 — the JSON-parsing fallback bug

The restarted run (`loterre_full_corpus_log3.txt`, active **2026-10-16 01:23 → 2026-10-19 06:29**, 81,660 bytes of log) ran for roughly 3 days before being deliberately killed to apply a fix for a bug discovered during this window.

**The bug**: inside `evaluate_loterre_v8.py`'s `classify()` function, a malformed-JSON model response used to raise an exception inside the *same* try block as the HTTP call itself — this skipped a substring-fallback check entirely and returned `None`. `run_loterre_corpus.py` would then silently write the hardcoded default label "référentiel" to the output file regardless of what the model had actually said, with no error surfaced anywhere visible.

**Fix applied, 2026-10-19**: the JSON-parsing step was moved outside the network try/except block, so a `JSONDecodeError` now falls through to the substring-matching fallback (checking the raw text for the literal words "référentiel"/"figuré") instead of discarding the model's real answer. Confirmed **zero new occurrences of this error since the fix.**

**Scope of the damage, precisely quantified**: `grep -c "ERROR: Expecting property" loterre_full_corpus_log3.txt` found **528 confirmed errors**, all from this one run. Every other available log (`log.txt`, `log2.txt`, `log4.txt`, `log5_gpu3.txt`) shows **zero** occurrences of this specific error string. The very first log (`log.txt`) is 0 bytes and unrecoverable, so this bug's presence or absence in whatever (if anything) ran before `log2.txt` cannot be verified either way — an acknowledged unknown, not assumed clean.

**How these 528 rows can be precisely located, worked out but not yet executed**: `log3.txt` interleaves `ERROR: Expecting property...` lines with periodic 50-row checkpoint lines (`[N/total_this_run, M total] elapsed=... eta=...`), in exact row-processing order, since the script always processes rows in a fixed, deduplicated, resume-filtered order. The run's checkpoint lines give a constant offset (this_run count minus total count) of **2,416** rows already done before this specific run started — meaning this run's own processed rows correspond to **output-file rows ~2,417 through ~31,684**, a contiguous, identifiable window, not scattered randomly through the file. Two remediation paths were worked out (not yet executed as of the most recent record checked): (1) a cheap/precise option — narrow each ERROR line to its surrounding ≤50-row checkpoint window, replay the corpus-loading/dedup logic to reconstruct exactly which rows fall there, and force-reclassify only those specific rows; (2) a simple/brute option — force-reclassify the entire ~29,268-row window regardless of which rows actually errored, at a cost of roughly 29,268 rows × ~8s/row ≈ 65 hours of GPU time but requiring no reconstruction work. **Explicit decision**: do not start either remediation until the main Loterre job reaches 100%, since the main job keeps writing new rows past row 31,684 and touching output rows mid-run risks corrupting the resume-by-key logic. This remains an open, scoped, deferred action item — not yet started as of 2026-10-21.

### 2026-10-19 onward — further restarts, current state

Two more log files exist after the fix: `loterre_full_corpus_log4.txt` (started 2026-10-19 10:36, 0 bytes) and `loterre_full_corpus_log5_gpu3.txt` (started 2026-10-20 00:59, the current active log as of this writing, dedicated to GPU 3). The ~14.5-hour gap between these two starts, and why `log4.txt` itself contains no printed output, could not be explained from any source checked — a genuine gap in the record, not resolved here. **A real, separate observability finding, confirmed by direct code inspection**: `run_loterre_corpus.py`'s CSV writer explicitly calls `out_f.flush()` on every row, but its progress-counter `print()` statement does not flush — meaning the log file can appear frozen for a long stretch (confirmed: `log5_gpu3.txt`'s last-modified timestamp sat at 2026-10-20 00:59 for over a day while real output kept growing) purely due to buffered stdout, not a stalled or broken job. The only reliable way to check real progress is the actual output file's row count, not the log.

**Current state, directly verified 2026-10-21**: `resultats/task1_loterre_labels.csv` contains **40,366 rows** (32,152 référentiel / 8,214 figuré — a 20.4% figuré rate), process PID 1326158 confirmed alive. Category breakdown: Milieux naturels 29,344, Vocabulaire du vivant 7,300, Activités humaines 1,942, Menaces écologiques 922, Climat 737, blank 120, and one single-row typo "Activés humaines" (vs. the correct "Activités humaines" elsewhere) — a negligible data-entry inconsistency, not a pipeline bug. No "ERROR" label values present in the current output, consistent with the JSON-bug fix having taken effect and the pre-fix 528 affected rows being a separable, already-scoped-and-deferred cleanup rather than an ongoing contamination.

**Pace and time-to-completion, computed from two real checkpoints spaced ~11.4 hours apart**: the full-run average pace (40,366 rows over the run's total elapsed time of roughly 2 days 1-2 hours) is **~812 rows/hour**, which would put total completion around **~6.7 days** from the original restart — close to the originally estimated ~5 days. However, the *most recent* measured pace (the last ~11.4 hours specifically) was dramatically slower, **~161 rows/hour** — a 5x slowdown, confirmed to correlate with the DGX node's GPU 3 (Loterre's own dedicated GPU) sitting at 98% utilization from other users' unrelated jobs, not from Loterre itself. At that degraded recent pace, the remaining ~90,206 rows would take roughly **23 more days**, for a total of **~25 days** from restart — a dramatically different number from the optimistic average-based estimate. Which figure actually holds depends entirely on how long the current server-wide contention persists, which cannot be predicted from available information; this document records both figures explicitly rather than picking one.
